You're right that the caching mechanism itself lives on the provider's server — but frameworks are very much responsible for *whether your inputs are cache-friendly*. The blame is legitimate, just often poorly explained. Here's the full picture:

## What providers actually cache

Anthropic (and others) do **prefix caching** — they hash a contiguous prefix of your input tokens and serve a cached KV state if the prefix matches exactly. Even one token difference at position N invalidates everything after N.

So the real question is: **who controls how stable that prefix is?** The framework does.

---

## How frameworks actively destroy cache hit rates

**1. Dynamic content injected too early**

If a framework puts anything volatile near the top of the system prompt — timestamps, session IDs, user metadata, retrieved memory — it breaks the prefix for *everything* that follows, including your static tool schemas and instructions.

```
// Bad — volatile content breaks the prefix early
System: "Session: abc123. Time: 2026-05-05T10:32Z. You are a helpful..."
         ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
         Everything after this is uncacheable

// Good — static content first, dynamic content last
System: "You are a helpful assistant. Tools: [...]. Rules: [...]"
User:   "[Retrieved context injected here instead]"
```

**2. Inconsistent tool schema ordering**

Some frameworks regenerate or reorder tool definitions per request. Since tool schemas are part of the input token stream, any reordering breaks the hash — even if the actual schemas are identical.

**3. For Anthropic specifically — missing explicit cache breakpoints**

Anthropic's caching isn't fully implicit like some other providers. You have to explicitly mark breakpoints with `cache_control: { "type": "ephemeral" }`. A framework that doesn't implement this correctly gets **zero** prompt caching benefit, regardless of how stable the prefix is. The framework has to actually call the API correctly.

**4. Non-deterministic message serialization**

Frameworks that re-serialize conversation history with slightly different whitespace, escape sequences, or field ordering across turns break prefix consistency even when the semantic content is the same.

---

## The split responsibility

| Responsibility | Who owns it |
|---|---|
| Actually storing/serving the cache | LLM provider |
| Placing `cache_control` breakpoints | **Framework / your code** |
| Keeping static content prefix-stable | **Framework architecture** |
| Not injecting volatile tokens early | **Framework architecture** |
| Cache TTL, eviction policy | LLM provider |

---

## Why this matters for Auwgent

This is actually a design advantage you can document. Since `prompt_gen.rs` has explicit control over how system prompts are assembled, you can guarantee:

1. Static blocks (agent persona, compiled tool schemas, rules) always come first and are stable across turns
2. Dynamic content (retrieved context, CFS temporal windows, prior turn summaries) gets appended at the end or injected at the user turn
3. Anthropic `cache_control` breakpoints are placed correctly at the boundary between static and dynamic sections

Frameworks like LangChain that build prompts through a pipeline of middleware chaining often can't give you this guarantee because intermediate steps can inject content anywhere. That's the architectural root of the problem — not the caching mechanism itself.

```
You are a helpful assistant
"not that old"

age: 10
user_name: Amihere

```

**The `ADDITIONAL CONTEXT` block is injected inside the system prompt, before all your static protocol content.** This means:

- Every different user → different system prompt → cache miss
- Every session with different metadata → cache miss
- All the valuable static content below it (blocks, tools, workflows, helpers, constraints) **never gets cached** because the prefix is already broken

---

## What the structure should look like

**System prompt** — 100% static, never changes between users or sessions:
```
You are an execution engine. Respond only with valid protocol blocks.
...
[all your blocks, tools, workflows, helpers, constraints]
```

**First user turn** — inject the dynamic context here instead:
```
[context]
age: 10
user_name: Amihere
id: '100'
[/context]

my name is Theophilus Amihere Junior...
```

Or alternatively, as a synthetic `assistant` prefill or a leading user message that carries session context. The key is: **anything that changes per user/session must never touch the system prompt.**

---

## The practical fix in `prompt_gen.rs`

Right now your prompt generator is probably doing something like:

```rust
// Bad — dynamic data bleeds into system prompt
let system = format!(
    "{base_persona}\n\n# ADDITIONAL CONTEXT\n{context}\n\n{protocol}",
    base_persona = ...,
    context = render_context(user_meta),  // <-- the problem
    protocol = ...
);
```

It should be:

```rust
// Good — system prompt is pure static
let system = format!("{base_persona}\n\n{protocol}");

// Dynamic context goes into the turns array, prepended to the first user message
let first_user_turn = format!("[context]\n{context}\n[/context]\n\n{user_input}",
    context = render_context(user_meta),
    user_input = initial_input
);
```

## What you gain

| | Before | After |
|---|---|---|
| System prompt | Unique per user | Shared across all users |
| Cache hit on system prompt | Never | Always (after first request) |
| Anthropic cache breakpoint placement | Meaningless | Goes at end of static system prompt |
| Cost over N turns | Full token price every time | KV cache served from turn 2+ |

# Cache-Aware Prompt Compilation in Auwgent

## The Problem

LLM providers implement prefix caching — if the leading tokens of a request match a previously cached sequence, the provider serves the KV state directly, cutting both cost and latency significantly. The cache breaks the moment any token in the prefix changes.

Agent frameworks routinely destroy cache efficiency by injecting dynamic, user-specific content directly into the system prompt. Every unique user produces a unique system prompt, which means a cache miss on every single request regardless of how much of the content is shared.

## The Root Cause

Auwgent's DSL allows inline interpolation inside the `prompt` block:

```
prompt: """
You are a helpful assistant
"The person is old {{ctx.age}}"
"""
```

At runtime, `{{ctx.age}}` produces a different token sequence per user — `10`, `25`, `47` — making the system prompt unique per request. Branch conditionals with static bodies are not a problem; they converge to a finite set of stable strings and cache naturally. The only expression that genuinely breaks caching is an inline value interpolation.

## Our Approach: Symbolic Indirection

The Auwgent compiler performs static analysis on the prompt AST. Any inline interpolation `{{ctx.x}}` found in the `prompt` block is replaced with a stable symbolic reference `@@x` at compile time. The system prompt becomes structurally identical across all users and sessions.

```
# Compiled system prompt — identical for every user
"The person is old @@age"
```

The actual values are deferred to a synthetic binding turn injected by the runtime at the start of each conversation, separate from any user message:

```
[bindings]
@@age = 10
@@user_name = Amihere
[/bindings]
```

## The Floating Binding Cursor

Across a multi-turn conversation, the synthetic binding turn always sits immediately before the current frontier user message. Once a turn receives a response and moves into history, the binding turn before it becomes a stable, cacheable entry. The bindings then re-attach before the next user message.

```
Request N:
  [SYSTEM]              ✓ cache hit
  [USER turn 1]         ✓ cache hit
  [ASSISTANT turn 1]    ✓ cache hit
  ...
  [SYNTHETIC bindings]  ✗ miss  (frontier)
  [USER turn N]         ✗ miss  (frontier)

Request N+1:
  [SYSTEM]              ✓ cache hit
  [USER turn 1]         ✓ cache hit
  [ASSISTANT turn 1]    ✓ cache hit
  ...
  [SYNTHETIC bindings]  ✓ cache hit  (now history, values fixed)
  [USER turn N]         ✓ cache hit  (now history, pure)
  [SYNTHETIC bindings]  ✗ miss  (new frontier)
  [USER turn N+1]       ✗ miss  (new frontier)
```

The cache miss is always exactly **-1 + all** — one miss on the current frontier, every prior turn a hit. This is the theoretical optimum for a system with dynamic runtime values.

The synthetic turn is a first-class runtime construct, distinct from user and assistant turns. This guarantees clean session management — user turns remain pure conversational content, and the binding layer is fully controlled by the runtime, invisible to both the developer and the model.
