# Rust DX Proposal + Implementation Plan

## Target DX

The intended user code should be:

```rust
use hello_agent::*;

struct MyTools;

impl AuwgentTools for MyTools {
    fn get_location(&self, _args: GetLocationArgs) -> String {
        "Tarkwa".into()
    }

    fn get_user_name_age(&self, _args: GetUserNameAgeArgs) -> Person {
        Person {
            name: "Theophilus".into(),
            age: 99.0,
        }
    }
}

struct MLogger;

impl AuwgentMiddleware for MLogger {
    fn name(&self) -> &str { "simple logger" }

    async fn on_run_start(&self, session: Session, _ctx: &Context) -> Session {
        println!("{session:#?}");
        session
    }

    async fn on_llm_start(&self, prompt: String, _ctx: &Context) -> String {
        let prefixed = format!("...system context...\n{prompt}");
        println!("sending: {prefixed}");
        prefixed
    }
}

struct Logger;

impl AuwgentIntentHandler for Logger {
    fn response_text(&self, intent: &Intent, _agent: &str) {
        println!("answer: {}", intent.text());
    }

    fn response_schema(&self, intent: &Intent, _agent: &str) {
        println!("schema: {:#?}", intent.response::<HelloOutput>());
    }

    fn tool_call(&self, intent: &Intent, _agent: &str) {
        println!("[tool call] {:#?}", intent);
    }

    fn tool_result(&self, intent: &Intent, _agent: &str) {
        println!("[tool result] {:#?}", intent);
    }

    fn error(&self, intent: &Intent, _agent: &str) {
        println!("error: {}", intent.message());
    }
}

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let agent = auwgent(AuwgentConfig {
        api_keys: HelloApiKeys {
            groq_api_key: Some(std::env::var("GROQ_API_KEY")?),
        },
        tools: MyTools,
        middleware: vec![MLogger],
        context: HelloContext {
            user_id: "u_123".into(),
        },
    })?;

    agent.on_intent(Logger);
    agent.run(None).await?;
    Ok(())
}
```

The happy-path rules are:

- `tools: MyTools`, not `HelloToolsRegistry::new(MyTools)`
- `middleware: vec![MLogger]`, not `vec![Arc::new(MLogger)]`
- `agent.on_intent(Logger)`, not only raw closure callbacks
- named event methods like `response_text()` and `tool_call()`
- typed args/results, no raw `serde_json::Value` in app code

---

## What Exists Today

## Generator today: `auwgent-compiler/crates/auwgent-codegen/src/rust.rs`

Current generated API already provides:

- generated tool trait, e.g. `HelloTools`
- generated arg structs like `HelloGetLocationToolArgs`
- generated result aliases like `HelloGetLocationToolResultValue`
- generated `HelloToolsRegistry`
- generated `HelloConfig`
- generated `HelloAgent`
- generic callback hooks:
  - `on_intent(FnMut(HelloIntent, &str) -> Option<IntentControl>)`
  - `on_intent_handler(HelloBaseIntentHandler)`
  - `on_intent_partial_handler(HelloBasePartialIntentHandler)`

Current DX leaks:

- `HelloToolsRegistry`
- middleware arc alias types
- enum-level callback style as the primary abstraction
- no high-level intent wrapper/accessor API
- handler trait is one generic `on_intent(...)`, not event methods

## Runtime today: `targets/rust/src/lib.rs`

Current runtime provides:

- `ToolRegistrar`
- `AuwgentConfig<Tools = ()>`
- `TypedAuwgent<Tools>`
- `MiddlewareRegistry = Arc<dyn Middleware>`
- `Middleware` trait with lifecycle hooks
- native tool registration through `register_tool_fn`
- middleware event plumbing via raw JSON-ish event values

Current DX constraints coming from runtime:

- config stores `Vec<MiddlewareRegistry>`
- config expects already-wrapped middleware
- tool registration is based on `ToolRegistrar`, so generated code introduces a registry wrapper
- middleware receives raw name/value instead of a higher-level intent wrapper

---

## Proposed End State

Split the solution into two layers:

## Layer 1: public ergonomic API

This is what generated bindings expose:

- `AuwgentTools`
- `AuwgentMiddleware`
- `AuwgentIntentHandler`
- `Intent`
- `Context`
- `Session`
- `AuwgentConfig<TTools, TMiddleware>`
- `auwgent(config)`

## Layer 2: internal runtime plumbing

This stays hidden:

- `ToolRegistrar`
- generated tool registry wrapper
- `Arc<dyn Middleware>`
- raw JSON conversion
- enum dispatch plumbing

The user should only touch Layer 1.

## File-by-File Plan

## 1. `auwgent-compiler/crates/auwgent-codegen/src/rust.rs`

This file owns almost all user-facing DX.

### Change A: stop exposing registry in generated config

Today:

```rust
pub struct HelloConfig {
    pub tools: HelloToolsRegistry,
    pub middleware: Vec<HelloMiddlewareRegistry>,
    ...
}
```

Change to:

```rust
pub struct HelloConfig<TTools = (), TMiddleware = ()> {
    pub tools: TTools,
    pub middleware: Vec<TMiddleware>,
    ...
}
```

And generated `auwgent(...)` should impose:

```rust
where
    TTools: HelloTools,
    TMiddleware: HelloMiddleware,
```

or conditional equivalents when tools/context are absent.

### Change B: keep generated registry, but make it internal

Do not delete the registry mechanism.
Just stop making users spell it.

Today generated code creates:

```rust
pub struct HelloToolsRegistry(pub Arc<dyn HelloTools>);
```

Keep something like that, but lower internally in `create_hello(...)`:

```rust
let tools = HelloToolsRegistry::new(config.tools);
```

So user code stays:

```rust
tools: MyTools
```

### Change C: change handler trait generation

Today:

```rust
pub trait HelloBaseIntentHandler {
    fn on_intent(&mut self, intent: HelloIntent, agent_name: &str) -> Option<IntentControl> {
        ...
    }
}
```

Replace with generated event-method trait:

```rust
pub trait HelloIntentHandler: Send + Sync + 'static {
    fn response_text(&self, _intent: &Intent, _agent: &str) {}
    fn response_schema(&self, _intent: &Intent, _agent: &str) {}
    fn tool_call(&self, _intent: &Intent, _agent: &str) {}
    fn tool_result(&self, _intent: &Intent, _agent: &str) {}
    fn tool_error(&self, _intent: &Intent, _agent: &str) {}
    fn tool_skipped(&self, _intent: &Intent, _agent: &str) {}
    fn workflow_call(&self, _intent: &Intent, _agent: &str) {}
    fn workflow_result(&self, _intent: &Intent, _agent: &str) {}
    fn helper_call(&self, _intent: &Intent, _agent: &str) {}
    fn helper_result(&self, _intent: &Intent, _agent: &str) {}
    fn error(&self, _intent: &Intent, _agent: &str) {}
    fn any(&self, _intent: &Intent, _agent: &str) {}
}
```

### Change D: generate `Intent` wrapper

Right now the generated code exposes `HelloIntent` enum directly.

Keep `HelloIntent`, but add:

```rust
pub struct Intent {
    inner: HelloIntent,
}
```

with helpers:

```rust
impl Intent {
    pub fn raw(&self) -> &HelloIntent;
    pub fn name(&self) -> &'static str;
    pub fn text(&self) -> &str;
    pub fn message(&self) -> &str;
    pub fn response<T: serde::de::DeserializeOwned>(&self) -> T;
    pub fn args<T: serde::de::DeserializeOwned>(&self) -> T;
    pub fn result<T: serde::de::DeserializeOwned>(&self) -> T;
}
```

This is the key to Python-SDK-style ergonomics.

### Change E: generate event dispatch function

Add a generated dispatcher:

```rust
pub fn dispatch_intent_event<H: HelloIntentHandler>(
    handler: &H,
    intent: &Intent,
    agent_name: &str,
) -> Option<IntentControl> {
    handler.any(intent, agent_name);

    match intent.raw() {
        HelloIntent::ResponseText(_) => {
            handler.response_text(intent, agent_name);
            None
        }
        HelloIntent::ResponseSchema(_) => {
            handler.response_schema(intent, agent_name);
            None
        }
        HelloIntent::ToolCall(_) => {
            handler.tool_call(intent, agent_name);
            None
        }
        ...
    }
}
```

If you later want interception/override support in event methods, only specific methods should return `Option<IntentControl>`.
For now the cleanest split is:

- middleware can override/skip
- intent handlers are observational

### Change F: make `agent.on_intent(...)` the high-level handler API

Today `on_intent(...)` is closure-based and `on_intent_handler(...)` is the trait wrapper.

Invert that.

Proposed generated API:

```rust
impl HelloAgent {
    pub fn on_intent<H>(&self, handler: H)
    where
        H: HelloIntentHandler;

    pub fn on_intent_raw<F>(&self, handler: F)
    where
        F: FnMut(HelloIntent, &str) -> Option<IntentControl> + Send + 'static;
}
```

That makes the better DX the default name.

### Change G: alias exports should expose the new trait names

Today aliases expose:

- `AuwgentBaseIntentHandler`
- `AuwgentBasePartialIntentHandler`

Replace/extend with:

- `AuwgentIntentHandler`
- `AuwgentIntent`
- `Intent`
- `Context`
- `Session`

The final generated names should read like a framework, not a transport layer.

## 2. `targets/rust/src/lib.rs`

This file owns runtime plumbing and should absorb the complexity the user currently sees.

### Change A: make middleware config generic over plain middleware values

Today:

```rust
pub struct AuwgentConfig<Tools = ()> {
    pub tools: Tools,
    pub middleware: Vec<MiddlewareRegistry>,
    ...
}
```

Change to:

```rust
pub struct AuwgentConfig<Tools = (), MiddlewareItem = ()> {
    pub tools: Tools,
    pub middleware: Vec<MiddlewareItem>,
    pub context: Option<Value>,
    pub api_keys: AuwgentApiKeys,
}
```

Then in `TypedAuwgent::new(...)`, lower middleware internally:

```rust
let middleware: Vec<MiddlewareRegistry> = config
    .middleware
    .into_iter()
    .map(|item| Arc::new(item) as MiddlewareRegistry)
    .collect();
```

with bounds:

```rust
MiddlewareItem: Middleware + 'static
```

This is what enables:

```rust
middleware: vec![MLogger]
```

### Change B: keep `ToolRegistrar`, but let generator own the wrap

The runtime can keep:

```rust
pub trait ToolRegistrar
```

No need to redesign the runtime around direct tool traits.

The important thing is:

- runtime still works with registrars
- generated code creates the registrar internally
- the user no longer sees the registrar

This is a good separation.

### Change C: add helper traits for middleware conversion if needed

If generic inference gets awkward, add internal helper trait:

```rust
pub trait IntoMiddlewareRegistry {
    fn into_registry(self) -> MiddlewareRegistry;
}

impl<T> IntoMiddlewareRegistry for T
where
    T: Middleware + 'static,
{
    fn into_registry(self) -> MiddlewareRegistry {
        Arc::new(self)
    }
}
```

Then lowering becomes simpler and generated code stays clean.

### Change D: optionally add typed middleware intent adapter later

Current middleware trait works on:

```rust
on_intent(&self, name: &str, value: &Value, ctx: &mut MiddlewareContext)
```

That is acceptable for now because middleware is a lower-level interception surface.

Do not block the DX rollout on redesigning middleware internals.

Possible later refinement:

- keep raw runtime middleware trait internally
- generate a high-level middleware adapter that receives `Intent`

But this can be phase 2.

```rust
pub struct HelloConfig<TTools = (), TMiddleware = ()> {
    pub api_keys: HelloApiKeys,
    pub tools: TTools,

```rust
pub trait HelloTools: Send + Sync + 'static {
    fn get_location(&self, args: HelloGetLocationToolArgs) -> HelloGetLocationToolResultValue;
    fn get_user_name_age(
        &self,
        args: HelloGetUserNameAgeToolArgs,

## Generated intent handler

```rust

    fn response_text(&self, _intent: &Intent, _agent: &str) {}
    fn response_schema(&self, _intent: &Intent, _agent: &str) {}
    fn tool_call(&self, _intent: &Intent, _agent: &str) {}
    fn tool_result(&self, _intent: &Intent, _agent: &str) {}
    fn error(&self, _intent: &Intent, _agent: &str) {}
    fn any(&self, _intent: &Intent, _agent: &str) {}
}
```

## Generated agent

```rust
impl HelloAgent {
    pub fn on_intent<H>(&self, handler: H)
    where
        H: HelloIntentHandler;

    pub fn on_intent_raw<F>(&self, handler: F)
    where
        F: FnMut(HelloIntent, &str) -> Option<IntentControl> + Send + 'static;
}
```

## Internal generated lowering

```rust
pub fn create_hello<TTools, TMiddleware>(
    config: HelloConfig<TTools, TMiddleware>,
) -> sdk::AuwgentResult<HelloAgent>
where
    TTools: HelloTools,
    TMiddleware: HelloMiddleware,
{
    let ir = sdk::parse_ir(include_str!("./hello.agent.json"))?;

    let sdk_config = sdk::AuwgentConfig {
        tools: HelloToolsRegistry::new(config.tools),
        middleware: config
            .middleware
            .into_iter()
            .map(|m| Arc::new(m) as sdk::MiddlewareRegistry)
            .collect(),
        context: Some(serde_json::to_value(config.context).map_err(|e| e.to_string())?),
        api_keys: config.api_keys.into(),
    };

    let inner = sdk::create_auwgent(ir, sdk_config)?;
    Ok(HelloAgent { inner })
}
```

This is where the ugly stuff belongs.

## Compatibility Plan

## Phase 1: additive migration

Keep old APIs working while adding the new ones.

Generated code should temporarily support both:

- `agent.on_intent_raw(...)`
- `agent.on_intent(...)`

and, if needed:

- `HelloToolsRegistry::new(...)`
- plain `tools: MyTools`

This avoids breaking existing examples.

## Phase 2: docs and examples move to the new path

Update examples to show:

- plain tool value
- plain middleware values
- named intent handler methods

Old APIs become escape hatches, not headline APIs.

## Phase 3: deprecate leaked plumbing

Eventually mark as less-preferred:

- public registry-focused examples
- `Arc::new(...)` in generated config examples
- `BaseIntentHandler` naming

No need to hard-break immediately.

---

## Concrete Work Items

## In `auwgent-compiler/crates/auwgent-codegen/src/rust.rs`

1. Update `generate_config(...)`
- make config generic over tool and middleware item types
- stop exposing registry types in public fields

2. Update `generate_tools(...)`
- keep registry generation
- ensure it is only used internally by generated factory

3. Replace `generate_handler_traits(...)`
- generate event-method intent trait
- generate `Intent` wrapper
- generate event dispatcher

4. Update `generate_agent(...)`
- rename closure API to `on_intent_raw(...)`
- make `on_intent(...)` take the new handler trait
- internally lower plain middleware values into `Arc`s
- internally lower plain tool values into registry

5. Update `generate_aliases(...)`
- export `AuwgentIntentHandler`
- export `Intent`
- keep raw enum aliases available

6. Update generator tests
- assert generated config uses plain generic tool/middleware fields
- assert `on_intent(...)` takes handler trait
- assert `on_intent_raw(...)` exists
- assert internal factory still constructs registry and arc conversions

## In `targets/rust/src/lib.rs`

1. Update `AuwgentConfig`
- add second generic parameter for middleware item

2. Update `TypedAuwgent::new(...)`
- accept generic middleware item type
- lower into `Vec<MiddlewareRegistry>` internally

3. Keep `ToolRegistrar` unchanged
- avoid unnecessary runtime redesign

4. Optionally add helper conversion trait for middleware
- only if it simplifies bounds and generated code

5. Keep raw middleware event model for now
- do not over-expand scope in the first pass

---

## Recommended Rollout Order

1. Runtime config generics in `targets/rust/src/lib.rs`
2. Generated config/factory lowering in `rust.rs`
3. New `AuwgentIntentHandler` trait + `Intent` wrapper
4. Rename current closure API to `on_intent_raw(...)`
5. Update examples/tests/docs

This order minimizes breakage and keeps each step understandable.

---

## Non-Goals for the First Pass

Do not try to solve all of these in the same change:

- async tool trait redesign
- proc macro design
- typed middleware internals
- TypeScript parity changes
- Python/Dart parity changes

The first pass should focus only on:

- plain config values
- event-method handler DX
- hiding registries and `Arc`

---

## Bottom Line

The implementation strategy is:

- keep the runtime plumbing mostly intact
- move ergonomics into generated Rust bindings
- lower plain user values into registries/arcs internally
- make event-method intent handlers the default surface

That gets the DX you want without forcing a large runtime rewrite.
