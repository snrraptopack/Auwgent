• Current middleware is a JSON bridge between the Rust engine and the host SDK.

  In Rust, the engine stores one middleware callback:

  middleware_event_handler: Arc<Mutex<Option<AsyncMiddlewareEventCallback>>>

  The bridge exposes it to the host:

  on_middleware_event(handler)

  So TypeScript/Python/Dart/Rust SDK code registers a host callback. When the engine reaches a
  lifecycle point, it builds a typed Rust payload, serializes it to JSON, sends that JSON string to
  the host callback, waits for an optional JSON string response, then parses the response back in
  Rust.

  The event model is defined in runtime/crates/auwgent-middleware/src/events.rs:

  #[serde(tag = "type", rename_all = "snake_case")]
  pub enum MiddlewareEvent {
      RunStart(RunStartPayload),
      RunComplete(RunCompletePayload),
      LlmStart(LlmStartPayload),
      LlmEnd(LlmEndPayload),
      Intent(IntentPayload),
      Error(ErrorPayload),
  }

  Each event carries an EventContext:

  pub struct EventContext {
      pub active_agent: String,
      pub stack: Vec<String>,
      pub root_agent: String,
      pub system_prompt: Option<String>,
      pub raw_block: Option<String>,
      pub model: Option<String>,
      pub provider: Option<String>,
      pub config: Option<Value>,
      pub url: Option<String>,
      pub headers: Option<Value>,
      pub api_key: Option<String>,
  }

  The transport helper is in parsing.rs:

  pub async fn fire_middleware_event(
      handler: Option<MiddlewareCallback>,
      event: Value,
  ) -> Option<Value> {
      let payload = serde_json::to_string(&event).ok()?;
      let response = handler?.clone()(payload).await?;
      serde_json::from_str(&response).ok()
  }

  So the shape is:

  Rust engine
    -> typed middleware event
    -> serde_json::Value
    -> JSON string
    -> host callback
    -> optional JSON string
    -> serde_json::Value
    -> parsed control/effects
    -> Rust engine mutates runtime state

  Example: llm_start.

  Rust builds:

  {
    "type": "llm_start",
    "prompt": "user input",
    "context": {
      "activeAgent": "RuntimeTest",
      "stack": ["RuntimeTest"],
      "rootAgent": "RuntimeTest",
      "model": "llama-3.3-70b-versatile",
      "provider": "groq",
      "config": {}
    }
  }

  The host can return:

  {
    "prompt": "modified input",
    "model": "different-model",
    "provider": "groq",
    "config": {},
    "headers": {},
    "api_key": "..."
  }

  Rust parses that with parse_llm_start_response() and applies it before calling the provider.

  For intents, host can return:

  { "skip": true }

  or:

  { "result": { "value": "overridden result" } }

  Rust parses that into:

  IntentControl::Skip
  IntentControl::Override { result }

  That is how middleware can skip tool calls, override tool results, mutate prompt/config/session,
  swallow errors, and force retries.

  Why DSL middleware reduces roundtrips:

  Today, every middleware event that needs logic must cross the Rust-host boundary.

  For a TypeScript SDK running native Rust through NAPI, that means:

  Rust -> JSON serialize -> NAPI -> JS callback -> maybe async JS -> JSON serialize -> NAPI -> Rust
  parse

  For Python/Dart/FFI/WASM, the boundary is different, but the pattern is the same: Rust pauses and
  asks the host what to do.

  If middleware is written in the DSL and compiled into IR/graph nodes, simple logic can run inside
  the Rust runtime directly:

  @middleware("logger")
  function Logger(event: MiddlewareEvents) {
      if event.on == "llmStart" {
          event.setPrompt(event.getPrompt() + " ha ha")
      }
  }

  That can become an internal middleware graph/function:

  Rust engine
    -> execute compiled middleware node locally
    -> apply effects

  No host callback needed for that case.

  So instead of:

  Rust -> host -> Rust

  you get:

  Rust -> compiled middleware evaluator -> Rust

  This reduces roundtrips for middleware that only touches runtime-owned data:

  - prompt mutation
  - session cleanup
  - context-derived config changes
  - model selection
  - tool filtering
  - intent skip/override based on args/context
  - retry/fallback policy
  - redaction of model outputs
  - simple logging into runtime event state

  Host middleware is still needed for external effects:

  - database reads/writes
  - filesystem access
  - secrets
  - network calls outside standard library
  - custom observability exporters
  - user infra integrations

  So the ideal v2 model is hybrid:

  Compiled DSL middleware:
    fast, portable, runs in Rust, no host roundtrip

  Host middleware:
    escape hatch for external systems

  This also matters more with graph/resumability. If middleware decisions are compiled and executed
  inside the graph runtime, they can be checkpointed as part of execution state:

  {
    "node": "agent:hello:n20",
    "event": "llm_start",
    "middleware": "Logger",
    "effects": {
      "prompt": "original prompt ha ha"
    }
  }

  That makes resume cleaner because the runtime knows exactly which middleware ran and what it
  changed, without depending on re-calling host code during recovery unless the middleware was
  explicitly host-backed.

but also maybe it it best we keep the middleware out of graph so it can be something like
ast or bytecode
hat gives you graph resumability where it matters, but avoids turning simple middleware into noisy
  graph structure.

  for on = llmend this runs when the model is done with what it doing

  is basically policy evaluation. It needs:

  - variable bindings
  - conditionals
  - field access
  - simple loops
  - string/object/array operations
  - event methods like getPrompt, setPrompt, skip, override
  - maybe context/session reads

  It does not naturally need:

  - node scheduling
  - edges
  - active node state
  - child graph state
  - graph-level resume
  - checkpoint after every expression

  So a bytecode VM or AST interpreter is cleaner.

  Recommended Runtime Shape

  GraphExecutor
    -> reaches lifecycle point
    -> builds MiddlewareEvent object
    -> MiddlewareRunner runs compiled DSL middleware locally
    -> applies collected event effects
    -> optionally calls host middleware
    -> checkpoints event effects
    -> continues graph execution

  So middleware execution becomes an embedded policy phase inside graph execution.

  AST vs Bytecode

  I’d start with AST interpretation unless you already know performance will matter.

  AST interpreter:

  {
    "middlewares": {
      "Logger": {
        "params": [{ "name": "event", "type": "MiddlewareEvents" }],
        "body": [
          {
            "type": "if",
            "condition": {
              "type": "binary",
              "op": "==",
              "left": { "type": "member", "object": "event", "property": "on" },
              "right": { "type": "literal", "value": "llmStart" }
            },
            "then": [
              {
                "type": "let",
                "name": "prompt",
                "value": {
                  "type": "call",
                  "callee": { "type": "member", "object": "event", "property": "getPrompt" },
                  "args": []
                }
              },
              {
                "type": "expr",
                "value": {
                  "type": "call",
                  "callee": { "type": "member", "object": "event", "property": "setPrompt" },
                  "args": [
                    {
                      "type": "binary",
                      "op": "+",
                      "left": { "type": "var", "name": "prompt" },
                      "right": { "type": "literal", "value": " ha ha" }
                    }
                  ]
                }
              }
            ]
          }
        ]
      }
    }
  }

  Later you can lower that to bytecode:

  LOAD_EVENT_FIELD on
  PUSH_CONST "llmStart"
  EQ
  JUMP_IF_FALSE L1
  CALL_EVENT getPrompt 0
  STORE_LOCAL prompt
  LOAD_LOCAL prompt
  PUSH_CONST " ha ha"
  ADD
  CALL_EVENT setPrompt 1
  L1:
  RETURN

  Bytecode is better long-term if you want:

  - faster repeated middleware execution,
  - stable portable runtime across targets,
  - smaller compiled artifacts,
  - validation before execution,
  - easier sandboxing,
  - potential WASM/browser performance.

  But AST is easier to debug and iterate while the language is still moving.
